# Хаптики в вебе: обзор вариантов (ресёрч 2026-08-03)

Собрано по запросу «поресёрчить разные библиотеки и ресурсы, нужно чтобы работало в iOS и
Android». Отправная точка — `mail-scroll`, где хаптик реализован как `navigator.vibrate(10)`
и **не ощущается на Pixel 4 в Chrome**; iOS-путь убран решением 2026-07-31.

Всё, что ниже, — состояние на **август 2026**. Область меняется патчами iOS, дату проверки
у каждого утверждения держать при себе.

---

## 1. Матрица: что реально работает

| Платформа | Механизм | Работает | Ограничение |
| --- | --- | --- | --- |
| Android Chrome / Firefox / Samsung Internet | `navigator.vibrate()` | ✅ | user activation во фрейме; системные настройки вибрации; амплитудой не управляем |
| iOS Safari (и все браузеры iOS — это WebKit) | Vibration API | ❌ | не реализован, в планах нет |
| iOS 18.0–26.4 | `<input type="checkbox" switch>` + программный `label.click()` | ✅ (до 26.4) | недокументированное поведение, **закрыто Apple в 26.5** |
| iOS 18.0–26.5+ | тот же switch, **реальный тап пальцем** по невидимому оверлею | ✅ | только на тап; момент задаёт палец, не код |
| iOS/Android внутри VK / Telegram | Bridge-метод хоста | ✅ | нужен запуск внутри клиента, не в браузере |
| iOS/Android в своей оболочке | Capacitor Haptics / нативный код | ✅ | нужна сборка и доставка приложения |
| Desktop | — | ❌ | железа нет; `navigator.vibrate` есть в API, но no-op |

**Короткий вывод.** Единого веб-API «хаптик на iOS и Android» не существует. Из браузера
кросс-платформенно закрывается **только тап**, и то разными механизмами на разных ОС. Жест,
таймер, «анимация доехала» — на iOS недостижимы из браузера в принципе.

## 2. Vibration API (Android)

Спека W3C, `navigator.vibrate(ms | [pattern])`, возвращает `boolean`.

**Гейты, из-за которых вызов молча не срабатывает:**

1. **User activation.** Chrome: «Blocked call to navigator.vibrate because user hasn't tapped on
   the frame or any embedded frame yet» — до первого касания фрейма вызов возвращает `false`.
   Активация «липкая»: один раз получена — действует до конца жизни документа, поэтому
   `setTimeout` и `transitionend` сами по себе не проблема. Проблема — вызов **до** первого
   `touchend`/`click` (например, из `touchmove` первого же свайпа) и вызов из `touchstart`
   (известная claim Chromium: «touchstart is not the right place to vibrate anyway»).
2. **Видимость документа.** Скрытая вкладка не вибрирует, отложенный таймер в фоне отбрасывается.
3. **Системные настройки Android.** Вибрация подчиняется «Звук и вибрация → Вибрация и хаптик»
   (в т.ч. отдельный тумблер тактильной отдачи при касании и ползунок интенсивности),
   беззвучному режиму / DND и режиму экономии батареи. При выключенной тактильной отдаче
   `vibrate()` возвращает `true`, но телефон молчит — это главная ловушка диагностики.
4. **Длительность.** Значения клиппуются сверху (порядка 10 с) и «схлопываются» снизу: короткий
   импульс физически не успевает раскачать мотор.

**Про длительность — ключевое для нашего бага.** Порог осмысленного отклика на Android
начинается примерно с **20 мс**: фреймворк Android требует поддержки минимум 20 мс между
контрольными точками огибающей, а исследования восприятия дают ~30 мс на переход «импульс →
вибрация». Для сравнения — пресеты популярной библиотеки `web-haptics`: `light` 15 мс,
`medium`/`heavy` до 35 мс, `selection` 8 мс. Наши **10 мс — ниже рабочего диапазона**, на LRA
Pixel 4 это законно может не ощущаться.

**«Интенсивность» в вебе не существует.** Vibration API умеет только «включить мотор на N мс».
Библиотеки, обещающие intensity/PWM, разбивают импульс на серию коротких включений — субъективно
меняется характер, но амплитудой это не управляет и на разных моторах звучит по-разному.
Управление амплитудой есть только в нативе (`VibrationEffect` c amplitude, Core Haptics).

## 3. iOS: switch-хак и его версии

WebKit добавил `<input type="checkbox" switch>` в Safari 17.4; с iOS 18.0 переключение этого
контрола даёт **системный tick**. Это не API, а побочный эффект нативного контрола.

| Вариант | iOS 18.0–26.4 | iOS 26.5+ | Пригоден для |
| --- | --- | --- | --- |
| Реальный тап по видимому switch | ✅ | ✅ (проверено) | только сам switch |
| Реальный тап по **невидимому** switch-оверлею поверх кнопки | ✅ | ✅ (проверено) | тап по любой кнопке/карточке |
| Программный `label.click()` (у `<label>`, связанного со switch) | ✅ | ❌ (проверено, 16 комбинаций) | любой момент, в т.ч. асинхронный |
| Программный `input.click()` | ❌ | ❌ | — |
| Смена `checked` без клика | ❌ | ❌ | — |

**Что закрыл патч — первоисточник и проверка на устройстве.** Коммит WebKit «Haptic feedback for
`<input type=checkbox switch>` should require user activation» (bug 285120 / rdar://142190653)
требует `processingUserGesture == true`: «It should not be possible to generate haptic feedback
from script alone». Формулировка допускала лазейку — программный клик **внутри** обработчика
реального жеста. **Проверено стендами №2 и №3 на iPhone (iOS 26.5+, 2026-08-03): лазейки нет.**

- Стенд №3 перебрал форму контрола (видимый / `opacity: 0` нормального размера / `opacity: 0.02` /
  накрытый непрозрачным слоем / `1×1` / за экраном / `pointer-events: none` / пустой label) и
  момент вызова (`click`, `touchstart`, `touchmove`, `touchend`, `setTimeout(0)`, `setTimeout(250)`,
  `rAF`, `transitionend`) — **хаптика нет ни в одной из 16 комбинаций**.
- Единственное срабатывание программной формы в стенде №2 (пункт 2.5) оказалось **ложным**: там
  `<label>` был кликабелен, и тик дал палец пользователя, а не `label.click()`. В стенде №3 такие
  случаи ловились меткой «⚠ РЕАЛЬНОЕ КАСАНИЕ» и не подтвердились.
- Работает только прямой тап: видимый switch и невидимый switch-оверлей поверх кнопки
  (пункты 1.1 и 1.2 стенда №2) — то есть приём `project-fathom`/`ios-haptics`.

Вывод: **на iOS 26.5+ форма и момент значения не имеют — значение имеет только то, что контрол
переключил палец.**

Два уточнения к прошлому стенду `mail-scroll` (2026-07-31):

- в стенде проверялся **клик по `input`**, тогда как рабочим у всех библиотек был
  **клик по связанному `label`** — то есть пункт «программный `click()` не работает» был
  проверен не в той форме;
- практического значения это уже не имеет: тестовый iPhone на **iOS 26.5+**, где Apple закрыла
  программный путь целиком. Итоговый вывод HANDOFF («хаптик получает только реальный тап»)
  остаётся верным, меняется его причина и срок жизни.

**Почему хак не годится для жеста** (не изменилось): в нужный момент — «шторка доехала»,
«прогресс перевалил за 50%» — пальца на контроле нет, а программно ткнуть его больше нельзя.
Плюс грабля из HANDOFF: интерактивный контрол в зоне жеста ловит клик, который всплывает и
коммитит состояние посреди свайпа.

**Скрывать контрол только `opacity: 0`** (+ `clip-path` под форму кнопки): у
`display/visibility: hidden` тап не проходит.

## 4. Библиотеки

Все четыре — обёртки над теми же двумя механизмами; ни одна не даёт возможности, которой нет
у голого API.

| Пакет | Что внутри | Оценка |
| --- | --- | --- |
| **`web-haptics`** (lochie, `mintlify.wiki/lochie/web-haptics`) | `navigator.vibrate` + пересчёт длительностей под «интенсивность» + fallback `hapticLabel.click()`; 11 пресетов (`light` 15 мс, `selection` 8 мс, `success` 30+40 мс…), хуки для React/Vue/Svelte | Полезны **пресеты как ориентир по длительностям**. Заявление доки «Mobile Safari (iOS 13+)» через Vibration API — **неверно**: на iOS работает не Vibration API, а switch-fallback, и он мёртв на 26.5+ |
| **`ios-haptics`** (tijnjh) | ~25 строк: создаёт `<input type="checkbox" switch>` абсолютным оверлеем на элемент (`opacity: 0`, `clip-path: inset(0 round 999px)`, `touch-action: manipulation`) | Честная реализация «тап по оверлею». Ровно то, что переживает патч 26.5 |
| **`use-haptic`** (posaune0423) | программный `label.click()`, iOS 18+ | Мёртв на iOS 26.5+ |
| **`project-fathom`** (m1ckc3s) | демо-песочница React, проверена на живом iOS 26.5 | Не библиотека — **эталон проверки**: подтверждает, что после патча живёт только прямой тап |

**Брать ли зависимость.** Нет. npm registry с рабочей сети недоступен (`techContext` §Среда),
а полезного кода здесь на 25 строк — если понадобится, вендорится файлом (прецедент —
`apps/index/src/vendor/qrcodegen.ts`).

## 5. Обходные пути через хост-контейнер

Единственный способ получить **настоящий хаптик на iOS в вебе** — чтобы страницу открывал не
Safari, а приложение-хост со своим мостом.

- **VK Mini App** — `VKWebAppTapticImpactOccurred` (Taptic Engine; документирован для iOS),
  рядом `VKWebAppTapticNotificationOccurred` / `VKWebAppTapticSelectionChanged`. Для VKUI-прототипов
  это самый близкий вариант: маршрут «прототип внутри VK» уже разобран в `techContext`
  §«Как прототип попадает на чужое устройство» — там же оговорка, что `vk-bridge` из npm не
  поставится и понадобится вендорить сборку или слать сырой `postMessage`.
- **Telegram Mini Apps** — `web_app_trigger_haptic_feedback` (`impact` с стилями,
  `notification`, `selection_change`), в SDK — `HapticFeedback.impactOccurred('light')`.
  Работает на iOS; по Android у трекера Telegram-Mini-Apps есть issue о неработающих
  `impactOccurred`/`selectionChanged` в отдельных версиях клиента — проверять на устройстве.
- **Своя оболочка** — Capacitor `@capacitor/haptics` (`impact`, `notification`, `selection`),
  PWAKit и подобные шеллы. Даёт полный контроль (вплоть до Core Haptics), ценой сборки и
  доставки приложения; на iOS для чужих устройств упирается в Apple Developer Program
  (отложен решением 2026-07-12).

Важно: это меняет **способ показа прототипа**, а не его код — веб-часть остаётся той же,
добавляется тонкий адаптер поверх `haptic()`.

## 6. Мифы и тупики

- **«PWA на iOS даёт хаптик»** — нет. Standalone-режим не добавляет ни Vibration API, ни
  доступа к Taptic Engine.
- **«Проиграть низкочастотный звук — получится вибрация»** — это звук в динамике, не хаптик;
  на тихом режиме и в наушниках рассыпается.
- **Gamepad `vibrationActuator.playEffect()`** — работает, но только для подключённого геймпада;
  к телефону в руке отношения не имеет.
- **W3C Web Haptics Community Group** — закрыта в апреле 2023, спеки не оставила.
- **Interop** — Vibration API предлагался как фокус-область и **не вошёл в Interop 2026**.
  То есть обещания «Safari скоро добавит» на 2026 год нет; косвенный сигнал интереса WebKit —
  только те самые нестандартные хаптики на switch.

## 7. Рекомендация для прототипов монорепо

**Принятые решения (2026-08-03):** на iOS в вебе хаптик не делаем, оверлей-на-тап не возвращаем;
мост VK Mini App отложен вместе с самим маршрутом; на Android чиним длительность по стенду.
Формулировки и причины — в `progress.md` §«Хаптик в вебе: ресёрч вариантов и решения».


1. **Android — чинить длительность.** Один импульс 20–35 мс вместо 10 мс; конкретное число —
   по стенду на живом устройстве, не «по аналогии» (значение всё равно требует подтверждения
   дизайнером, см. пометку в `mail-scroll/HANDOFF.md`).
2. **iOS в браузере — не обещать.** В спеке прототипа хаптик на жесте помечать как «только
   натив/хост-контейнер». Тап при желании закрывается switch-оверлеем (`ios-haptics`-приём),
   но ценой интерактивного контрола в зоне жеста — в `mail-scroll` от этого отказались.
3. **Если нужен полноценный хаптик на iOS для демо** — показывать прототип внутри VK Mini App
   (или своей оболочки), см. §5 и раздел маршрутов в `techContext`.
4. **API в коде оставлять одной точкой** (`haptic()`), чтобы бэкенд (vibrate / bridge / шелл)
   менялся в одном файле.

### Чеклист «почему хаптик не сработал»

1. `typeof navigator.vibrate === 'function'`? (iOS Safari — сразу нет.)
2. Что вернул `navigator.vibrate(...)` — `false` значит гейт (нет user activation / документ скрыт).
3. Было ли к этому моменту касание страницы? Вызов из `touchmove` **первого** жеста — до активации.
4. Длительность ≥ 20 мс?
5. Системные настройки устройства: тактильная отдача включена, интенсивность не на минимуме,
   не беззвучный режим/DND, не режим экономии батареи.
6. Это точно браузер, а не встроенный webview мессенджера?
