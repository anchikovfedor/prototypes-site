# Conventions

## Анатомия прототипа

Прототип — отдельное приложение в `apps/<name>/`:

```
apps/<name>/
  package.json        # name: @proto/app-<name>; зависит от @proto/kit
  vite.config.ts      # react() + optimizeDeps.exclude ['@proto/kit']
  tsconfig.json       # extends ../../tsconfig.base.json
  index.html
  src/
    main.tsx          # createRoot + <App/>
    App.tsx           # <PrototypeRoot target=...><Content/></PrototypeRoot>
    screens/          # экраны = VKUI Panel'и
    components/       # локальные компоненты (например, Framer Motion micro-interactions)
    modals/           # ModalPage/ModalCard
  HANDOFF.md          # заметки для разработки
  NOTES.md            # опционально: веб-внутренности (см. §Передача в нативную разработку)
```

Правило изоляции: прототип **не импортирует** код других прототипов. Общее — только из
`@proto/kit`. Так папку `apps/<name>` можно поднять в продуктовый репозиторий.

## Таргеты

- `mobile-app` — весь вьюпорт, платформа iOS/Android, одноколоночные push-переходы,
  скролл внутри AppRoot (`embedded`/`contain`).
- `desktop-web` — VKCOM, полная ширина, многоколоночные раскладки (`SplitLayout`).
- `adaptive` — реагирует на ширину окна.

Таргет задаётся в `App.tsx`: `<PrototypeRoot target="...">`.

**Рамку устройства не рисуем** (решение пользователя, 2026-07-07): никакого мокапа телефона
вокруг прототипа — ни в ките, ни в самих прототипах. Прототип занимает весь вьюпорт;
смотреть в размере устройства = devtools-эмуляция или реальный телефон. Компонент
`PhoneFrame` из `@proto/kit` удалён — не возвращать.

## Минимальные входные данные прототипа

Перед сборкой зафиксировать минимальный набор Figma-артефактов (не угадывать):

- **Per-state макет** — валидный node-id (или ссылка) на **каждое** UI-состояние прототипа
  (напр. свёрнутая сетка + раскрытый экран; пустое/заполненное; до/после). Состояние берём из
  **рендер-макета**, а не реконструируем из initial-кадра анимации — иначе геометрия плывёт.
- **Motion-node** — узел Figma Motion: источник точных easing / длительности / пружин переходов.

Требования к узлам: лежат в **основном файле** (не в branch и не в «🗑️ Draft»); node-id
протухают — если узел не резолвится, переспросить, а не подставлять старый. Значения тянуть
через Figma MCP: `get_design_context` / `get_metadata` / `get_variable_defs`. Ссылки на
состояния и Motion-node фиксируются в `apps/<name>/HANDOFF.md` → секция «Источник / вход».

## Источник значений анимации (строгий гейт)

Все параметры анимации — easing, длительности, задержки/stagger, смещения, размеры, blur,
opacity, поворот, тени, порядок появления — брать **только** из одного из двух источников:

1. **Таймлайн Figma Motion** через `get_motion_context`. Грабли: на корневом Smart-Animate
   символе таймлайн часто пуст (`timelineDurationMs: null`) — вызывать с **`recursive: true`**,
   значения лежат на дочерних узлах в `codeSnippets.motionDev` (`initial` / `animate` /
   `transition`, `times` / `ease`). Loop-демо: активная фаза = `times[1] × durationMs`
   (напр. `0.25 × 2000 = 500 мс`), дальше — hold для зацикливания.
2. **Таблица-спецификация**, если дизайнер её дал. Считается спекой и ответ в переписке —
   если пользователь назвал конкретные значения (так работали `cards-drum` и `mail-scroll`,
   где Motion-node в файле не оказалось). Записывать в HANDOFF с пометкой «спека дизайнера».

**Видео-референс (mp4 из After Effects) спекой НЕ является.** По нему можно понять механику
(что за чем двигается, что остаётся на месте), но восстанавливать кривые и длительности по
кадрам нельзя: 30 сэмплов на переход не задают easing, а сам референс может показывать
**более старую итерацию дизайна**, чем присланные макеты (так было в <internal-ticket> — другой фон и
другой контент). Механику — берём, числа — спрашиваем.

**Запрещено** подставлять значения «на глаз», по аналогии, из памяти или из прошлых сессий.
Если какого-то значения нет ни в таймлайне, ни в спеке — **остановиться и явно спросить
пользователя**, не подставляя догадку. Любое неизбежное приближение (то, что CSS/движок не
повторяет 1:1) — назвать явно и согласовать.

Длительности и задержки (включая stagger) — по **сетке 50 мс** и диапазонам из
`review-animations/STANDARDS.md` (Short 100–200 / Medium 250–400 / Long 450–600 /
Extra long 700–1000 мс); ревью-гейт флагает отклонения. Некратное значение из
Figma-таймлайна — противоречие источников: остановиться и согласовать с пользователем.

### Пружины: форма записи, переносимая в натив

Прототипы уходят в разработку под iOS и Android, поэтому пружину записываем так, чтобы
платформенный разработчик взял число **без пересчёта**. Переносится **пара (T, ζ)**:

- **T** — период собственных колебаний, сек. SwiftUI: `response`, он же `duration`
  в `spring(duration:bounce:)`. **Не** время успокоения.
- **ζ** — коэффициент затухания, безразмерный. SwiftUI: `bounce = 1 − ζ`.
  Compose: `dampingRatio`. ζ=1 — без отскока.

Пара не зависит от единиц (px / pt / dp) — потому и переносится. Физическая форма при
`mass = 1`: `ω₀ = 2π/T`, `stiffness = ω₀²`, `damping = 2ζω₀`; у Framer Motion и Compose
масса по умолчанию 1, поэтому число `stiffness` у них **общее**. Обратная проверка на
стороне натива в одну строку: `T = 2π/√stiffness`.

**Откуда берутся T и ζ.** Тот же гейт, что и у кривых: таймлайн Figma или спека. Если
дизайнер утвердил кривую с длительностью, а перейти нужно на пружину — **выводить численно**
(подгонкой к утверждённой кривой), а не назначать на глаз; вывод и расхождение записывать в
HANDOFF. Так сделано в `mail-scroll`: для каждой длительности спеки найдена пружина с ζ=1,
минимально расходящаяся с `cubic-bezier(0.2, 0, 0, 1)`, — вышло отношение **T ≈ 0.8 × D**.

**Пружину — только позиции.** Прозрачность, цвет и подобное оставлять на кривой: пружина
выносит значение за границы диапазона, и физического смысла в этом нет.

**Сетка 50 мс к пружинам не применяется** — у них нет фиксированной длительности.
Нормируется `T`; ревью-гейт об этом не знает, расхождение объяснять в отчёте.

**Грабли Framer Motion** (проверено по исходнику `motion-dom` 12.42, не по докам):

1. `visualDuration` ≠ SwiftUI `duration`: там `ω₀ = 2π / (visualDuration × 1.2)`, то есть
   `SwiftUI duration = visualDuration × 1.2`. Одно и то же число в двух движках даёт пружины,
   расходящиеся на 20% — поэтому в коде держим **физическую форму**.
2. Duration-форма (`duration`/`visualDuration` + `bounce`) **принудительно обнуляет
   velocity** — передать скорость жеста через неё нельзя.
3. `MotionValue.jump()` сбрасывает отслеживание скорости, а `animate()` берёт её именно у
   переменной (`getVelocity()`). Кадры жеста писать через **`set()`**; скорость «протухает»
   после 30 мс без обновлений (`MAX_VELOCITY_DELTA`).

**Передача скорости — то, ради чего пружины и берут.** Проверять её замером, а не на глаз:
одна дистанция, одна точка отпускания, разный темп жеста → сравнить пройденную долю остатка
через 100 мс. И помнить про побочный эффект: с ненулевой скоростью **даже критически
задемпфированная пружина проскакивает цель**, если отпустить у самого конца хода. Если выход
за край виден (уехали скругления, показалась подложка) — ограничивать **отрисовку** (`clamp`),
а не саму пружину.

## Воркфлоу реализации

Двухфазный, с жёстким гейтом апрува между статикой и анимацией:

1. **Вход** — зафиксировать Figma-артефакты (см. выше) → проверка: ссылки резолвятся через Figma MCP.
2. **Статика** — собрать вёрстку всех состояний **без анимаций и переходов** → проверка:
   визуальное совпадение с макетами + **апрув пользователя**. Жёсткий гейт: до апрува статики
   анимацию не делаем. Процедура этапа — скилл **`proto-static`** (Figma MCP → статичная
   вёрстка → скриншот-сверка headless Chrome ↔ Figma → запрос апрува).
3. **Анимация** — только после апрува. **Обязательно** свериться со скиллом
   **`emil-design-eng`** (стандарты motion: easing, длительности, физика, перфоманс, a11y)
   **до** реализации. Переходы: VKUI по умолчанию, Framer Motion / WAAPI точечно; движение,
   которое ведут пальцем, — пружиной (§«Пружины»), чтобы отпускание наследовало скорость.
   Значения — строго из таймлайна Figma / спеки (см. «Источник значений анимации»).
   Проверка: уважает `prefers-reduced-motion` и тумблер Motion. Процедура этапа — скилл **`proto-animate`**
   (проверяет гейт апрува статики, ведёт по источникам значений).
4. **Ревью анимаций (жёсткий гейт).** **Обязательно** прогнать скилл **`review-animations`**
   на диффе анимации перед апрувом: `/review-animations` или вызов моделью на выходе фазы
   `proto-animate` (вендорен в `.claude/skills/review-animations/`; `disable-model-invocation`
   снят 2026-08-09 — флаг пришёл от апстрима и гейт не защищал, ревьюер всё равно субагент
   `proto-animation-review`). Проверка: вердикт
   **Approve**, не осталось hard-flags. При **Block** — исправить и перепрогнать; апрув не
   выдаётся, пока вердикт не Approve.
5. **Передача** — скилл **`proto-handoff`**: DoD-чеклист (см. ниже), финализация
   `HANDOFF.md`, `npm run build:site`, деплой с проверкой по контенту (`techContext.md`
   §«Деплой»), опционально обновление публичного зеркала (`scripts/export-public.mjs`).

Этапы 2, 3 и 5 проходят через **свои** этапные скиллы `proto-static` / `proto-animate` /
`proto-handoff` (`.claude/skills/`): в них зафиксированы пошаговые процедуры, а прохождение
фаз отмечается чекбоксами в `apps/<name>/HANDOFF.md` §«Статус фаз».

Изолированные, контекст-тяжёлые части фаз выполняют **субагенты** (`.claude/agents/`),
возвращая отчёт/спеку/вердикт в основной тред; апрув, пуш и Edit-работа остаются в нём:
скриншот-сверка статики — `proto-static-verify` (шаг 2); извлечение motion-значений из
таймлайна Figma — `proto-motion-extract` (шаг 3); ревью анимаций — `proto-animation-review`
(шаг 4); проверка деплоя по контенту — `proto-deploy-verify` (шаг 5).

Motion-скиллы **вендорены в `.claude/skills/`** из **github.com/emilkowalski/skills**:
`emil-design-eng` (стандарты motion, шаг 3), `review-animations` + `STANDARDS.md` (гейт-ревью,
шаг 4). Оба обязательны и не пропускаются. `review-animations` переведён на русский и
адаптирован под проект (проектные триггеры: трассируемость значений, тумблер Motion, сетка
50 мс; таблица длительностей Short/Medium/Long/Extra long) — upstream-синк теперь вручную. Upstream содержит ещё `animation-vocabulary`
(в проект не вендорен). Встроенный `web-animation-design` — вспомогательно. Каталог
**transitions.dev** (`github.com/Jakubantalik/transitions.dev`) — **только референс идей**;
не ставить пишущим CSS-скиллом: его `:root`-токены и `t-*`-классы конфликтуют с VKUI-токенами
и своей дизайн-системой, а переходы экранов уже есть из VKUI.

### Передача в нативную разработку

Если прототип уезжает в **натив** (iOS/Android), веб-реализация переиспользованию не подлежит,
и рабочий журнал в `HANDOFF.md` только мешает. Тогда файл режется надвое (введено на
`mail-scroll` / `mail-scroll-v2`, 2026-08-10):

- **`HANDOFF.md` — спека поведения.** Остаётся только то, что разработчик воспроизведёт на
  любой платформе: состояния и карта переходов, жесты (зона старта → ход → порог → исход),
  таблица анимаций с источником на каждую строку, пружины в форме **(T, ζ)** с колонками
  SwiftUI/Compose, моменты хаптиков, reduced motion, расхождения с макетом, принятые после
  ревью отступления, «чего в прототипе нет».
- **`NOTES.md` — веб-внутренности.** Разметка и CSS-переменные, компоненты VKUI и Framer
  Motion, обходы браузерных ограничений, замеры headless, мок-данные и ассеты, детализация
  Figma-узлов. Нужны тому, кто вернётся к самому прототипу.
- **Проверка разреза — по числам, не по строкам:** все числовые токены старого HANDOFF должны
  найтись в новой паре файлов. Плюс грепом убедиться, что в HANDOFF не осталось веб-терминов
  (имена CSS-переменных и классов, VKUI, Framer, CSS, Safari, headless, z-index, touch-action).
- **Версии прототипа — самодостаточные файлы, а не «дельта».** Отличия помечаются прямо
  в тексте; читать оба HANDOFF не должно требоваться.
- **Публичная ссылка на спеку** (если разработке нужен URL, а не файл): прототип добавляется
  в `DOC_ONLY_APPS` в `scripts/export-public.mjs` — наружу уходит только `HANDOFF.md`,
  в `handoff/<name>/` публичного зеркала. Исходники и `NOTES.md` остаются приватными.
  Детали и грабли — `techContext.md` §«Деплой».

## Как добавить прототип

Основной путь — скилл **`/new-prototype <имя> <таргет>`**: копирует `apps/_template`,
переименовывает пакет, ставит зависимости и **сам регистрирует** прототип в лаунчере
(`register.mjs`, идемпотентно, `status: 'wip'`). Затем:

1. Поправить `title`/`description` в `apps/index/src/prototypes.ts` (скаффолдер ставит
   плейсхолдеры).
2. Собрать экраны и навигацию (`useStack` для push, `Epic` для табов, `ModalRoot` для шторок).
3. Заполнить `HANDOFF.md`.

Вручную (без скилла): скопировать `apps/_template` → `apps/<name>`, поменять `name` в
`package.json`, `npm install`, зарегистрировать в `prototypes.ts`, дальше шаги 2–3.

## Совместная работа

- Модель: **ветка на прототип → PR в `main`**. CI на PR: typecheck всех workspace +
  `format:check` + `build:site`. Важно: branch protection на приватном Free-плане
  **недоступна** (проверено 2026-07-12) — «в `main` только через PR» это конвенция, а не
  принуждение; вопрос защиты отложен вместе с решением о публичности репо.
- **Апрувы при самообслуживании** (когда прототипы делают дизайнеры команды): статику
  апрувит **дизайнер-автор прототипа** (он и есть заказчик точности); машинный гейт
  анимации — `review-animations` (вердикт Approve обязателен); merge в `main` — через PR
  с зелёным CI и ревью владельца (@anchikovfedor) на первых прототипах автора, дальше —
  по договорённости.
- Конфликт-поверхность между авторами минимальна (прототипы изолированы в `apps/<name>`):
  общие точки — `apps/index/src/prototypes.ts` (одна строка на прототип) и
  `package-lock.json`. Лечение: `git rebase origin/main`, затем `npm install`
  (пересоберёт лок), закоммитить результат.
- Общий слой (`packages/kit`, `.claude/`, `memory-bank/`, `scripts/`, `.github/`) меняется
  только через ревью владельца — закреплено в `.github/CODEOWNERS`.

## Нейминг

- Имена переменных/функций/компонентов — английские.
- Папка прототипа — kebab-case (`apps/checkout-flow`).
- `nav`-идентификаторы панелей — строковые (`'feed-list'`), совпадают с `activePanel`.

## Шрифты и рендеринг

Применимо ко всем прототипам.

- **Сглаживание (обязательно при кастомных шрифтах).** VKUI **не** задаёт `font-smoothing`,
  поэтому на macOS Chrome текст рендерится субпиксельно — заметно жирнее, чем в Figma
  (там grayscale). Симптом «шрифт по параметрам как в Figma (вес 500), но ощущается толще» =
  именно это. Лечится глобально:
  ```css
  body {
    -webkit-font-smoothing: antialiased;
    -moz-osx-font-smoothing: grayscale;
  }
  ```
- **Подключение кастомного шрифта (напр. VK Sans Display).** Файлы → `apps/<name>/src/fonts/`,
  `@font-face` в `src/fonts.css` (импортируется из `App.tsx`) с **относительным** `url('./fonts/…')`.
  Важно: относительный путь, **не** абсолютный `/fonts/…` из `public/` — иначе Vite не хеширует
  ассет и не переписывает путь под подпапочный `base`, и на деплое `/<repo>/<name>/` шрифт 404-ит
  (проверено на cards-drum). Маппинг весов: Regular→400, Medium→500 (отдельные файлы, не faux-bold).
- **Файлы шрифтов НЕ в git** (`apps/*/src/fonts/*.ttf` и `apps/*/public/fonts/*.ttf` в
  `.gitignore`): VK Sans Display проприетарный. Локально — положить в `src/fonts/`. **Для
  публичного деплоя** (CI не видит gitignore-файлы) — раскладывать в CI из base64-секретов
  перед сборкой: `.github/workflows/deploy.yml` → шаг «Restore proprietary fonts», секреты
  `VK_SANS_MEDIUM_B64` / `VK_SANS_REGULAR_B64` (`gh secret set … < <(base64 file)`). Без файлов
  прототип молча падает на системный fallback-стек. Файл на gh-pages скачиваем (неизбежно для
  рендера веб-шрифта), но в git/публичное зеркало не попадает.
- **Где применять.** `--vkui--font_family_accent` у VKUI = **системный** стек, не VK Sans. На
  акцентных текстах (заголовки) задавать семейство явно:
  `font-family: 'VK Sans Display', var(--vkui--font_family_base, sans-serif)`.
  Подписи/футноуты в Figma — `fontFamilyBase` (не Display), их семейство обычно не трогаем.

## Definition of done для прототипа

- Вход зафиксирован в `HANDOFF.md`: Figma-состояния + Motion-node (секция «Источник / вход»).
- Статика всех состояний заапрувлена (гейт) до начала анимации.
- Запускается `npm run dev -w apps/<name>` и собирается `npm run build`.
- Переходы между экранами работают и выглядят как задумано.
- Анимации уважают `prefers-reduced-motion` и тумблер Motion.
- Ревью `review-animations` зелёное (вердикт Approve).

## Проверка результата: мерить, а не смотреть

Расхождения с макетом и поведение жестов проверяем инструментально — «на глаз» пропускает
и ложно срабатывает (проверено на `mail-scroll`, где визуально «равномерный блюр» оказался
неработающими слоями):

- **геометрия** — CDP `Runtime.evaluate` → `getBoundingClientRect` / `getComputedStyle`,
  не пиксельные прикидки по скриншоту;
- **пиксельный дифф** Figma ↔ рендер — средняя дельта и % пикселей с расхождением, плюс
  выборка по интересующей полосе (диффа по всему экрану мало: локальный дефект в нём тонет);
- **профиль резкости построчно** (средний модуль горизонтальной производной) — если проверяем
  размытие: показывает, где блюр реально есть, а где его нет;
- **эффект правки** — сравнением «включено / выключено»: если отключение свойства меняет
  картинку на 0, оно не работает вовсе;
- **жесты** — синтезированным тачем (`Input.dispatchTouchEvent`), а не только сменой классов.

Грабли headless-стенда (стоили ложных выводов):

- скрипты переиспользуют `--user-data-dir` → браузер отдаёт **CSS из кэша**; обязателен
  `Network.setCacheDisabled`;
- открывать состояние «хаком» через `classList` нельзя, если логика живёт в React-состоянии —
  внутреннее состояние не меняется и тест даёт ложный провал;
- `touchEnd` **сам порождает** `click` — добавлять `dispatchMouseEvent` к тапу нельзя,
  получится двойное срабатывание;
- на проде сверять после смены hash бандла: CDN несколько минут отдаёт прошлый.
